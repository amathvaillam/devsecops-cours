# Chapitre 04 — CI avec GitHub Actions

Objectif : comprendre ce qu'est l'intégration continue et lire un workflow.

## 1. Le concept

**CI = intégration continue** : à chaque push/PR, un serveur rejoue
automatiquement les étapes de vérification (install → tests → build) sur une
machine **vierge** et publie le résultat. But : détecter un bug en minutes,
pas en jours, et ne jamais laisser du code cassé entrer dans `main`.

## 2. L'anatomie du workflow (`.github/workflows/ci.yml`)

GitHub exécute chaque fichier YAML de ce dossier comme un workflow.

```yaml
on:
  push: { branches: [main] }          # déclencheurs
  pull_request: { branches: [main] }  # → le check vert/rouge sur tes PR
```

```yaml
jobs:
  test:
    runs-on: ubuntu-latest            # VM vierge, jetée après la run
    services:
      postgres:                       # conteneur d'appoint (mini compose)
        image: postgres:16-alpine
        options: --health-cmd "pg_isready -U tpuser -d tpdb" ...
    steps:
      - checkout@v4      # télécharge ton code
      - setup-node@v4    # installe Node 20 (même version que le Dockerfile)
      - Initialiser le schéma   # psql -f db/init.sql (voir le piège ↓)
      - npm ci           # dépendances exactes du lockfile
      - npm test         # tes 7 tests, DB_HOST=localhost → le service
  build:
    runs-on: ubuntu-latest            # tourne EN PARALLÈLE du job test
    steps: [ checkout, docker build ]
```

Points clés :
- **Le service postgres** = exactement notre `docker run` jetable du
  chapitre 01, automatisé. Le health-check remplace notre boucle
  « base prête ».
- **Vierge à chaque run** : le résultat ne dépend pas de ta machine.
  « Ça marche chez moi » n'existe plus — c'est le but.
- **La boucle de feedback** : le statut vert/rouge apparaît sur la PR
  avant le merge. Le code cassé ne passe plus inaperçu.

### ⚠️ Le piège qu'on a rencontré (vécu !)

Les conteneurs de service démarrent **avant** l'étape `checkout` : à ce
moment-là, ton code n'est pas encore téléchargé sur la machine. Monter
`db/init.sql` dans le service échoue donc (Docker crée un dossier vide →
`psql: error: could not read from input file: Is a directory`).

**La solution** : appliquer le schéma dans une étape dédiée, *après* le
checkout, avec un client psql :

```yaml
- name: Initialiser le schéma de la base
  run: sudo apt-get update && sudo apt-get install -y postgresql-client &&
       PGPASSWORD=tppassword psql -h localhost -U tpuser -d tpdb -f db/init.sql
```

Leçon générale : **l'ordre d'exécution des étapes est une source de bugs
classique en CI**. Toujours vérifier ce qui existe au moment où une étape
tourne.

## 3. Pourquoi GH Actions (et Jenkins ensuite)

- GH Actions : zéro installation, feedback immédiat, gratuit pour les repos
  publics. Idéal pour la CI.
- Jenkins (chapitre 05) : les mêmes concepts, mais auto-hébergé — son terrain
  de prédilection est la **CD** : build → push DockerHub → déploiement, avec
  credentials et tags versionnés.

## Vérification

- [ ] La run de CI est verte sur la PR `feat/tests`
- [ ] Après merge, la run sur `main` est verte aussi
- [ ] Un push cassé (exercice : casser un test volontairement) rend la run rouge

## Réutilisable : quoi copier, quoi changer

- Le squelette du workflow (on/services/jobs/steps) : identique partout
- À adapter : la version du langage, les commandes de test, l'image du service
- Le bloc `services:` : réutilisable tel quel pour toute app qui a besoin
  d'une base en CI
